# 强缓存/协商缓存

在前端优化和浏览器缓存机制中，**强缓存** 和 **协商缓存** 是两个非常核心的概念，它们可以显著提升页面加载速度、减轻服务器压力。

---

## 🧊 一、强缓存（**强制缓存 / 强制使用本地缓存**）

### ✅ 定义：

强缓存表示：**在规定的时间内，浏览器直接使用本地缓存文件，不会向服务器发起请求**。

---

### 📦 实现方式：

通过响应头的以下字段实现：

| 响应头字段      | 示例                                     | 说明                                |
| --------------- | ---------------------------------------- | ----------------------------------- |
| `Expires`       | `Expires: Wed, 22 May 2025 10:00:00 GMT` | HTTP/1.0 设定的过期时间（绝对时间） |
| `Cache-Control` | `Cache-Control: max-age=3600`            | HTTP/1.1 推荐使用（相对时间）       |

如果还在有效期内，浏览器直接使用缓存文件（200 from disk/memory cache）。

---

### 📌 特点：

- 不发起请求，速度最快
- 依赖时间控制
- 一旦缓存过期，才进行下一步的协商缓存检查

---

## 🔁 二、协商缓存（**对比缓存 / 条件缓存**）

### ✅ 定义：

协商缓存表示：**浏览器向服务器发起请求，同时带上缓存标识，服务器对比后决定是否使用缓存内容**。

---

### 📦 实现方式：

通过两个响应头 + 两个请求头完成协商过程：

| 响应头（第一次返回时） | 对应的请求头（下一次请求时携带） | 作用                           |
| ---------------------- | -------------------------------- | ------------------------------ |
| `Last-Modified`        | `If-Modified-Since`              | 比较资源最后修改时间           |
| `ETag`（实体标签）     | `If-None-Match`                  | 比较资源内容是否变更（更精准） |

---

### 📌 过程示例：

1. 第一次请求返回：

```http
200 OK
Cache-Control: no-cache
Last-Modified: Tue, 25 May 2025 10:00:00 GMT
ETag: "abc123"
```

2. 下一次请求时浏览器发送：

```http
GET /style.css
If-Modified-Since: Tue, 25 May 2025 10:00:00 GMT
If-None-Match: "abc123"
```

3. 如果资源没变化，服务器返回：

```http
304 Not Modified
```

浏览器继续使用本地缓存，但确认过是最新的。

---

### 📌 特点：

- 会发起请求，但不会下载内容（若没变化）
- 相比强缓存，响应速度略慢
- 更适合频繁更新的资源

---

## 🔍 强缓存 vs 协商缓存 对比表：

| 特性             | 强缓存                     | 协商缓存                |
| ---------------- | -------------------------- | ----------------------- |
| 是否发请求       | ❌ 不发请求                | ✅ 发请求               |
| 响应状态码       | `200 (from cache)`         | `304 Not Modified`      |
| 是否使用本地缓存 | ✅ 是                      | ✅ 是（条件成立时）     |
| 控制字段         | `Cache-Control`, `Expires` | `Last-Modified`, `ETag` |
| 优先级           | ✅ 优先于协商缓存          | -                       |

---

## 💡 浏览器缓存流程图：

```text
资源请求 →
    是否命中强缓存（未过期）？
        → 是：使用本地缓存，返回 200 (from cache)
        → 否：
            发起请求，带上协商缓存字段（如 ETag）
            服务器是否资源有变化？
                → 没变：返回 304 Not Modified
                → 有变：返回新资源，状态码 200 OK
```

---

## 🛠 最佳实践建议

| 场景                    | 推荐策略                             |
| ----------------------- | ------------------------------------ |
| 静态资源（JS/CSS/图片） | 使用强缓存，搭配版本号（`v=123`）    |
| 动态接口数据            | 使用协商缓存（ETag / Last-Modified） |
| 高频更新资源            | 使用短强缓存 + 协商缓存结合          |

# Cookie

是的，**Cookie 可以通过 JavaScript 控制**，但有一些重要的前提条件和限制。

---

## ✅ JS 操作 Cookie 的基本方式

### 1. 读取 Cookie（`document.cookie`）

```js
console.log(document.cookie);
// 输出类似：'username=alice; theme=dark'
```

- 只能读到**当前域名下、非 HttpOnly 的 Cookie**
- 返回的是一个字符串，需手动解析

---

### 2. 写入 Cookie

```js
document.cookie = "username=alice";
document.cookie = "theme=dark; path=/; expires=Fri, 31 Dec 9999 23:59:59 GMT";
```

- 每次设置只影响一个键值对，重复设置会覆盖
- 可以加上：

  - `expires`：过期时间
  - `max-age`：存活秒数
  - `path`：作用路径
  - `domain`：作用域
  - `secure`：仅 HTTPS 可用
  - `SameSite`：CSRF 防护设置

---

## ❌ JS 无法访问的 Cookie（受限制）

| Cookie 属性         | JS 可访问？ | 说明                                            |
| ------------------- | ----------- | ----------------------------------------------- |
| 没有 `HttpOnly`     | ✅          | 可以通过 JS 读写                                |
| 有 `HttpOnly`       | ❌          | **不能通过 JS 访问**（防止 XSS）                |
| 跨域设置的 Cookie   | ❌          | 需 CORS + `withCredentials`，但 JS 通常无法访问 |
| `Secure` 但非 HTTPS | ❌          | 只能在 HTTPS 下设置和访问                       |

---

## ⚠️ 安全提示

- **敏感信息（如 token）不要放在可被 JS 访问的 Cookie 中**，应使用 `HttpOnly` + `Secure`
- Cookie 是 XSS 攻击的常见目标，防护建议：

  - 对敏感 Cookie 设置 `HttpOnly`
  - 开启 `SameSite=Lax` 或 `Strict` 限制第三方请求
  - 使用 HTTPS + `Secure` 属性

---

## ✅ 示例：设置带过期时间的 Cookie

```js
function setCookie(name, value, days) {
  const d = new Date();
  d.setTime(d.getTime() + days * 24 * 60 * 60 * 1000);
  const expires = "expires=" + d.toUTCString();
  document.cookie = `${name}=${value};${expires};path=/`;
}
```

# 路由编码

**URL 编码**（URL encoding，也叫 percent-encoding），是为了确保 URL 在互联网上传输时的安全性和兼容性。

---

### ✅ 原因：URL 对字符的要求

URL（统一资源定位符）中**只能包含 ASCII 字符**，不允许出现空格、中文、特殊符号（如 `#`, `?`, `&` 等）。为了保证这些字符能被安全传输和正确解析，浏览器或框架会自动将它们编码成符合标准的形式。

---

### ✅ 什么会被编码？

- 中文、日文等非 ASCII 字符
- 空格（编码为 `%20`）
- 特殊符号，如：

  - `/`、`?`、`#`、`&`、`=`、`+` 等有特定含义的字符
  - `"`、`<`、`>`、`%` 等可能引起解析歧义的字符

---

### ✅ 例子：

原始路径：

```text
/note/ai/数据结构
```

编码后变成：

```text
/note/ai/%E6%95%B0%E6%8D%AE%E7%BB%93%E6%9E%84
```

这是 `"数据结构"` 的 UTF-8 编码再以百分号表示。

---

### ✅ 实际用途示例：

假如你传一个 URL 到服务器中：

```js
fetch(`/search?q=数据`);
```

浏览器实际上发送的是：

```text
/search?q=%E6%95%B0%E6%8D%AE
```

这确保服务器能正确解析成原始字符串 `"数据"`，而不会误将 `?q=数据` 中的 `?` 或其他字符当作路径分隔符等。

---

### ✅ 总结：

| 项目               | 是否允许在 URL 中直接使用 | 是否需要编码 |
| ------------------ | ------------------------- | ------------ |
| 英文和数字         | ✅ 是                     | ❌ 否        |
| 中文               | ❌ 否                     | ✅ 是        |
| 特殊符号（如 `&`） | ❌ 否                     | ✅ 是        |
