# 多线程 & 多进程

多线程并发处理和多进程并发处理在并发模型上有一些关键的区别。了解这些区别可以帮助你选择合适的技术方案来解决特定的并发问题。下面是这两种并发处理的主要区别：

### 1. **内存管理与资源隔离**

- **多线程**：

  - 所有线程共享同一进程的内存空间（堆、全局变量、文件描述符等）。
  - 线程之间的通信比进程之间的通信更容易，因为它们共享内存，可以通过共享变量直接交换数据。
  - 但是，多个线程在访问共享内存时需要通过同步机制（如互斥锁、信号量等）来避免竞争条件（race conditions），否则可能会导致数据不一致或者程序崩溃。

- **多进程**：

  - 每个进程都有独立的内存空间，进程间的资源完全隔离。
  - 进程之间的通信比线程之间的通信复杂一些（常用的通信方式包括管道、消息队列、共享内存、套接字等）。
  - 由于内存的隔离，进程间互不干扰，适合处理高隔离度的任务。例如，当一个进程崩溃时，不会直接影响到其他进程。

### 2. **执行模型与并发能力**

- **多线程**：

  - 多线程在一个进程内并发执行多个任务，共享资源可以降低开销（内存共享、上下文切换快等）。
  - 适合 **CPU 密集型任务** 和 **I/O 密集型任务**，特别是在单核和少数核心的环境下，线程池能够有效管理大量并发任务。
  - 线程的上下文切换开销相对较小，但一旦线程数量过多，线程调度和同步的成本会增加，可能导致性能瓶颈。

- **多进程**：

  - 每个进程运行在独立的地址空间和内存中，相互之间没有共享资源。
  - 在 **多核 CPU** 环境下，多进程模型能更好地利用系统资源。每个进程可以运行在不同的 CPU 核心上，分担更多的计算任务，从而达到更高的并发处理能力。
  - 进程的上下文切换相对较慢，因为它们有独立的内存空间、打开的文件句柄等，且需要涉及到操作系统层面的切换。

### 3. **稳定性与容错性**

- **多线程**：

  - 线程之间共享内存和资源，因此某个线程的崩溃可能导致整个进程的崩溃，影响所有其他线程的执行。
  - 在多线程应用中，必须特别小心同步和内存管理，避免线程间的竞态条件、死锁等问题。

- **多进程**：

  - 每个进程有独立的内存和资源，一个进程崩溃不会直接影响其他进程。
  - 适合在高可用性要求较高的场景中使用，因为进程可以通过监控机制进行恢复和重启，而不影响其他进程。

### 4. **开销**

- **多线程**：

  - 线程创建和销毁的开销相对较小。因为线程共享内存，创建线程时只需要分配少量的线程栈，线程间的上下文切换较轻。
  - 适用于短时任务和需要频繁创建销毁线程的场景。

- **多进程**：

  - 进程的创建和销毁相对较重，每个进程需要独立的内存空间和资源，操作系统会进行额外的内存分配、映射等操作。
  - 进程间的通信比线程间通信要复杂，可能需要额外的机制来交换数据，如消息队列、管道、共享内存等。
  - 适用于高负载和需要高隔离性的场景，但进程的开销较大。

### 5. **共享资源**

- **多线程**：

  - 线程间可以直接共享资源（如共享变量、文件描述符等），这使得线程间的通信比较高效。
  - 然而，多个线程同时访问共享资源可能会引发竞态条件、死锁等问题，必须通过同步机制来确保数据一致性。

- **多进程**：

  - 进程间的资源独立，不能直接共享内存。为了在进程间传递数据，需要使用进程间通信机制（IPC），如共享内存、管道、消息队列等。
  - 进程间通信开销较大，因为需要通过操作系统进行数据传递，数据的共享和同步也需要额外的开发工作。

### 6. **编程模型**

- **多线程**：

  - 编程模型相对简单，线程的创建、销毁和管理都可以通过现有的线程库来完成，线程的调度由操作系统或线程池管理。
  - 需要额外注意线程间同步、共享资源的访问控制等。

- **多进程**：

  - 多进程编程模型更复杂，进程之间的通信和同步通常更为困难，通常需要依赖操作系统提供的 IPC 机制。
  - 在 Node.js 中，常用的模块如 `cluster`、`child_process`，或者使用进程池管理大量并发任务。

---

### 总结对比：

| 特性/维度          | 多线程                                   | 多进程                                 |
| ------------------ | ---------------------------------------- | -------------------------------------- |
| **内存隔离**       | 线程共享内存                             | 进程内存独立                           |
| **通信开销**       | 线程间通信高效（直接共享内存）           | 进程间通信较复杂，需要使用 IPC         |
| **稳定性**         | 某个线程崩溃可能影响整个进程             | 一个进程崩溃不会影响其他进程           |
| **上下文切换开销** | 较小，线程切换比进程切换快               | 较大，进程切换需要更多资源和时间       |
| **适用场景**       | CPU 密集型、小任务并发，频繁创建销毁线程 | CPU 密集型、大任务并发，长时间运行进程 |
| **开发复杂度**     | 需要注意线程安全、同步问题               | 需要处理进程间通信、管理多个进程       |

### 何时选择 **多线程**：

- 多线程适合 **共享资源**，且任务间需要频繁交换数据、对内存的开销敏感的场景。
- 例如：需要大量小任务并发执行的情况（如爬虫、并发 HTTP 请求等）。

### 何时选择 **多进程**：

- 多进程适合 **需要隔离** 或者 **内存占用较高**，且需要利用多核 CPU 进行并行计算的任务。
- 例如：高并发 Web 服务、数据处理、大规模图片处理等。

## 多线程 & 多进程实践（在 node 后端中，使用 puppeteer 创建多个页面，并发处理截图请求）

在 Node.js 后端使用 Puppeteer 创建多个页面并发处理截图请求时，通常有两种常用的方案：

1. **使用 `worker_threads` 模块** — 多线程并发处理。
2. **使用 `cluster` 模块** — 多进程并发处理。

### 方案选择依据：

- **Puppeteer 的限制**：Puppeteer 是基于 Chromium 的浏览器自动化工具，每个页面的创建和操作本质上是 CPU 和内存密集型任务。在单线程环境下，运行大量并发的 Puppeteer 页面可能会导致性能瓶颈。因此，通常推荐使用 **多线程** 或 **多进程** 来处理并发任务。

- **选择方案的关键因素**：

  - **`worker_threads`**：适合 **CPU 密集型任务**，例如多个页面的操作需要大量计算。每个 Worker 线程共享主线程的内存，但在 Node.js 中它们各自有独立的 V8 引擎实例。
  - **`cluster`**：适合 **I/O 密集型任务**，特别是处理多个并发请求，例如 Web 服务。每个子进程拥有自己的事件循环和内存，能有效地利用多核 CPU。

### 推荐方案：**`worker_threads` 模块**

由于 Puppeteer 操作是多页面并发截图等密集任务，每个页面需要进行渲染和截图，**`worker_threads`** 模块更适合这种场景。它能够在单个进程中创建多个线程，每个线程独立执行任务，并且拥有相对独立的内存空间，可以并行处理多个 Puppeteer 页面，提升并发处理能力。

### 示例：使用 `worker_threads` 和 `Puppeteer` 进行并发截图

```javascript
const puppeteer = require("puppeteer");
const { Worker, isMainThread, parentPort } = require("worker_threads");
const path = require("path");

// 主线程
if (isMainThread) {
  const screenshotUrls = [
    "https://example.com/page1",
    "https://example.com/page2",
    "https://example.com/page3",
  ];

  const workers = [];

  screenshotUrls.forEach((url, index) => {
    // 每个 URL 使用一个独立的 worker 来处理截图
    const worker = new Worker(__filename);
    workers.push(worker);

    // 向 worker 发送 URL 以进行截图
    worker.postMessage(url);

    // 接收 worker 发送的截图结果
    worker.on("message", (imageBuffer) => {
      // 保存图片或处理图片
      const imagePath = path.join(__dirname, `screenshot_${index}.png`);
      require("fs").writeFileSync(imagePath, imageBuffer);
      console.log(`截图保存为: ${imagePath}`);
    });

    // 错误处理
    worker.on("error", (error) => {
      console.error("Worker 错误:", error);
    });

    worker.on("exit", (exitCode) => {
      if (exitCode !== 0) {
        console.error(`Worker 退出，退出码: ${exitCode}`);
      }
    });
  });
} else {
  // Worker 线程：处理每个页面的截图
  const browserOptions = { headless: true }; // 设置 Puppeteer 启动选项
  const pageOptions = { width: 1280, height: 720 }; // 页面尺寸

  parentPort.on("message", async (url) => {
    const browser = await puppeteer.launch(browserOptions);
    const page = await browser.newPage();
    await page.setViewport(pageOptions);

    try {
      // 打开网页并截图
      await page.goto(url);
      const screenshotBuffer = await page.screenshot();

      // 将截图结果发送给主线程
      parentPort.postMessage(screenshotBuffer);
    } catch (error) {
      console.error(`错误：无法截图 ${url}`, error);
    } finally {
      await browser.close();
    }
  });
}
```

### 解释：

- **主线程**：

  - 创建多个 Worker，每个 Worker 负责处理一个 URL 的截图请求。
  - 使用 `worker.on('message', ...)` 监听 Worker 返回的截图数据（这里假设截图数据是一个图片 buffer）。
  - 主线程保存每个 Worker 返回的截图文件。

- **Worker 线程**：

  - 每个 Worker 线程接收到一个 URL 后，使用 Puppeteer 启动浏览器实例，并打开对应页面进行截图。
  - 截图结果通过 `parentPort.postMessage()` 发送回主线程。

### 优势：

- **并发处理**：每个 Worker 线程独立运行，互不干扰，可以并发处理多个页面的截图。
- **内存优化**：通过线程共享内存空间，避免了进程间通信的开销。
- **Puppeteer 资源隔离**：每个 Worker 线程都有自己的 Puppeteer 实例和浏览器实例，保证了任务的独立性。

### 其他方案：使用 `cluster` 模块

如果你希望利用 **多核 CPU** 来提高性能，尤其是当请求数量非常庞大时，使用 `cluster` 模块是另一种选择。

```javascript
const puppeteer = require("puppeteer");
const cluster = require("cluster");
const http = require("http");
const os = require("os");

const numCPUs = os.cpus().length;

if (cluster.isMaster) {
  // 主进程：创建多个子进程
  console.log(`主进程 ${process.pid} 正在运行`);

  for (let i = 0; i < numCPUs; i++) {
    cluster.fork();
  }

  cluster.on("exit", (worker, code, signal) => {
    console.log(`工作进程 ${worker.process.pid} 退出`);
  });
} else {
  // 子进程：每个进程处理截图任务
  http
    .createServer(async (req, res) => {
      const url = req.url.slice(1); // 假设 URL 就是截图的目标地址

      const browser = await puppeteer.launch({ headless: true });
      const page = await browser.newPage();
      await page.goto(url);
      const screenshotBuffer = await page.screenshot();
      await browser.close();

      res.writeHead(200, { "Content-Type": "image/png" });
      res.end(screenshotBuffer);
    })
    .listen(8000);

  console.log(`工作进程 ${process.pid} 正在监听 8000 端口`);
}
```

### 结论：

- 如果你的任务主要是 **CPU 密集型**（如大规模的页面截图），建议使用 `worker_threads` 来并行化处理。
- 如果你希望更好地 **利用多核 CPU** 并且任务主要是 **I/O 密集型**（如并发的 Web 请求），则可以考虑使用 `cluster` 来创建多个进程。

### 性能考虑：

- `worker_threads` 是多线程实现，可以在相同的进程内更好地管理内存和资源。
- `cluster` 适合更高负载的场景，多个进程运行在不同的 CPU 核心上，可以分担更多的任务，尤其适合 Web 服务类的应用。

# 第三方库 `workerpool`

1. 创建线程池 worker.ts

ESM 与 CommonJS 的区别：在 CommonJS 模块中，你可以直接使用 `__filename` 和 `__dirname`，而在 ESM 中，它们是不可用的。`import.meta.url` 提供了获取模块路径的替代方案。

```ts
import path from "path";
import workerpool from "workerpool";
import { fileURLToPath } from "url";

const __filename = fileURLToPath(import.meta.url);
const __dirname = path.dirname(__filename);

// 创建线程池，最大并发数为 4
const pool = workerpool.pool(path.resolve(__dirname, "./test.js"), {
  maxWorkers: 4,
  workerType: "thread",
});

export { pool };
```

2. 定义线程函数 thread.js

```js
import workerpool from "workerpool";
import puppeteer from "puppeteer";

let browser;
let htmlPage;

const initPage = async () => {
  const start = performance.now();
  browser = await puppeteer.launch({
    headless: true,
    // executablePath: isProd ? '/app/cache/puppeteer' : undefined,
  });
  htmlPage = await browser.newPage();
  await htmlPage.setCacheEnabled(false);
};

const DEFAULT_VIEW_WIDTH = 750;
const DEFAULT_VIEW_HEIGHT = 480;
const DEFAULT_VIEW_SCALE = 1;

const takeHtmlStrScreenshot = async ({
  url,
  html,
  screenshotParams = {},
  value = "{}",
}) => {
  const {
    width = DEFAULT_VIEW_WIDTH,
    height = DEFAULT_VIEW_HEIGHT,
    scale = DEFAULT_VIEW_SCALE,
    fromView,
    transparent,
  } = screenshotParams;

  const t1 = performance.now();

  if (!htmlPage) {
    await initPage();
  }

  let pageInfo = htmlPage;
  if (pageInfo == null) {
    throw new Error("no available page");
  }

  const t2 = performance.now();

  try {
    await htmlPage.setViewport({
      width: width,
      height: height,
      deviceScaleFactor: scale,
    });

    const t3 = performance.now();

    const t4 = performance.now();

    await htmlPage.setContent(html);

    const t5 = performance.now();

    // waitForFunction是轮询执行
    await htmlPage.waitForFunction(
      () => {
        const imgs = Array.from(document.querySelectorAll("img"));
        return imgs.every((img) => img.complete);
      },
      { timeout: 10000 }
    ); // 设置一个合理的超时时间，比如 3 秒

    const t6 = performance.now();

    const screenshotType = transparent === true ? "png" : "jpeg";

    const screenshotBuffer = await htmlPage.screenshot({
      optimizeForSpeed: true,
      fullPage: !fromView,
      fromSurface: true,
      type: screenshotType,
      omitBackground: transparent,
    });

    const t7 = performance.now();

    console.log("takeHtmlStrScreenshot===>", [
      t2 - t1,
      t3 - t2,
      t4 - t3,
      t5 - t4,
      t6 - t5,
      t7 - t6,
    ]);

    return screenshotBuffer;
  } catch (error) {
    // pageInfo.stopUsing();
    throw error;
  }
};

// a deliberately inefficient implementation of the fibonacci sequence
function fibonacci(n) {
  if (n < 2) return n;
  return fibonacci(n - 2) + fibonacci(n - 1);
}

// create a worker and register public functions
workerpool.worker({
  fibonacci: fibonacci,
  takeHtmlStrScreenshot,
});
```
