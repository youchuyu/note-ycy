# @connectrpc

在前端开发和分布式系统中，了解远程过程调用（RPC）及其现代实现（如 `@connectrpc`）对于构建高效、可扩展的应用程序至关重要。([Microsoft Learn][1])

---

## 🔹 什么是 RPC？

**RPC（Remote Procedure Call，远程过程调用）** 是一种通信协议，允许程序调用远程计算机上的函数，就像调用本地函数一样，而无需关注底层的网络通信细节。([woshinlper.com][2])

**主要特点：**

- **透明性**：调用远程函数的方式与本地函数相同，简化了开发流程。

- **跨语言支持**：通过接口定义语言（IDL），如 Protocol Buffers，RPC 支持不同编程语言之间的通信。

- **高性能**：相比传统的 HTTP API，RPC 通常具有更低的延迟和更高的吞吐量。

常见的 RPC 框架包括 gRPC、Apache Thrift、Dubbo 等。([Apache Dubbo][3])

---

## 🔹 什么是 @connectrpc？

`@connectrpc` 是一组用于构建兼容浏览器和 gRPC 的 HTTP API 的库，旨在简化开发过程，提供类型安全的客户端和服务器实现。([vchitai.medium.com][4])

**核心特点：**

- **多协议支持**：支持 gRPC、gRPC-Web 以及 Connect 自定义协议，满足不同场景的需求。([GitHub][5])

- **类型安全**：通过使用 Protocol Buffers，确保客户端和服务器之间的数据结构一致，减少运行时错误。([npm][6])

- **跨平台**：提供多种语言的实现，包括 Go、JavaScript、TypeScript 等，适用于多种开发环境。

- **易于集成**：与现有的工具链和框架（如 Node.js、React）无缝集成，降低了上手难度。

Connect 项目已于 2024 年 4 月 13 日被 Cloud Native Computing Foundation（CNCF）接纳为 Sandbox 项目，进一步证明了其在云原生生态中的潜力。([CNCF][7])

---

## 🔹 @connectrpc 的应用场景

- **前端与后端通信**：在前端应用中，通过 `@connectrpc` 提供的客户端库，可以方便地调用后端服务，享受类型安全和高性能的通信。([npm][8])

- **微服务架构**：在微服务架构中，使用 `@connectrpc` 构建服务之间的通信接口，确保各服务之间的高效协作。

- **跨平台应用**：对于需要在多个平台（如 Web、移动端）上运行的应用，`@connectrpc` 提供统一的通信协议，简化了开发和维护工作。

---

总之，RPC 提供了一种高效、透明的远程通信方式，而 `@connectrpc` 则在此基础上，结合现代开发需求，提供了更易用、更灵活的解决方案，特别适合当前多平台、多语言的开发环境。

## 应用示例

```
// use-client.ts
import { useMemo } from "react";
import { type DescService } from "@bufbuild/protobuf";
import { createConnectTransport } from "@connectrpc/connect-web";
import { createClient, type Client } from "@connectrpc/connect";

// This transport is going to be used throughout the app
const transport = createConnectTransport({
  baseUrl: "https://demo.connectrpc.com",
});

/**
* Get a promise client for the given service.
*/
export function useClient<T extends DescService>(service: T): Client<T> {
  // We memoize the client, so that we only create one instance per service.
  return useMemo(() => createClient(service, transport), [service]);
}
```

# Protobuf

`@connectrpc` 与 Protocol Buffers（简称 Protobuf）之间的关系密切，主要体现在数据结构定义和通信协议方面。

---

### 🧩 Protobuf 的角色：数据结构定义与序列化

Protobuf 是 Google 开发的一种高效、跨语言的数据序列化协议。它允许开发者使用 `.proto` 文件定义数据结构和服务接口，然后通过 `protoc` 编译器生成对应语言的代码，实现数据的序列化和反序列化。([知乎专栏][1], [博客园][2])

**主要特点：**

- **高性能**：相比 JSON 或 XML，Protobuf 序列化后的数据更小，解析速度更快。([博客园][3])

- **跨语言支持**：支持多种编程语言，如 Go、Java、Python、JavaScript 等。([维基百科][4])

- **向后兼容**：通过字段编号机制，支持数据结构的演进而不破坏旧版本的兼容性。

Protobuf 常被用于定义 RPC 接口和消息格式，是许多 RPC 框架（如 gRPC、Connect）的基础。

---

### 🔗 `@connectrpc` 与 Protobuf 的关系

`@connectrpc` 是一组用于构建兼容浏览器和 gRPC 的 HTTP API 的库，旨在简化开发过程，提供类型安全的客户端和服务器实现。它使用 Protobuf 作为接口定义语言（IDL），通过 `.proto` 文件定义服务和消息结构，然后生成相应的客户端和服务器代码。

**集成方式：**

1. **定义服务**：使用 `.proto` 文件定义服务接口和消息结构。

2. **生成代码**：使用 `protoc` 编译器和 `@connectrpc` 提供的插件生成对应语言的客户端和服务器代码。

3. **实现逻辑**：在服务器端实现生成的服务接口，在客户端调用生成的客户端代码进行远程调用。([阿里云开发者社区][5])

这种方式确保了客户端和服务器之间的数据结构一致性，提高了开发效率和代码的可维护性。

---

### ⚙️ 总结

Protobuf 提供了高效、跨语言的数据结构定义和序列化机制，而 `@connectrpc` 则利用 Protobuf 定义的接口和消息结构，生成类型安全的客户端和服务器代码，简化了构建高性能、可扩展的 API 的过程。

通过这种集成方式，开发者可以更专注于业务逻辑的实现，而无需关注底层的通信细节，提升了开发效率和应用的可维护性。

# DNS

好的，我们来系统地讲一下 **DNS（Domain Name System，域名系统）**，这是互联网的基础服务之一。

---

## 🧩 一、什么是 DNS

DNS 就像互联网的 **“电话簿”**：

- 人类易记的域名（如 `www.example.com`）
- 对应计算机使用的 IP 地址（如 `192.168.1.1` 或 `2606:2800:220:1:248:1893:25c8:1946`）

DNS 的核心功能就是 **域名 → IP 地址的解析**，让浏览器或其他客户端能找到服务器。

---

## 🏗️ 二、DNS 的组成部分

1. **域名 (Domain Name)**

   - 由多级标签组成，右到左分级：

     ```
     www.example.com
     |   |      |
     子域名 域名  顶级域
     ```

2. **DNS 服务器类型**

   - **根服务器（Root Server）**：管理顶级域名（TLD）信息
   - **顶级域服务器（TLD Server）**：管理 `.com`, `.org` 等信息
   - **权威 DNS 服务器（Authoritative Server）**：存储域名实际解析记录
   - **递归 DNS 服务器（Recursive Resolver）**：用户本地或运营商提供，负责查找最终 IP

3. **DNS 记录类型**

   - **A**：IPv4 地址
   - **AAAA**：IPv6 地址
   - **CNAME**：别名（指向其他域名）
   - **MX**：邮件交换
   - **NS**：域名服务器
   - **TXT**：文本记录（SPF/DKIM 等）
   - **SRV**：服务记录

---

## 🔄 三、DNS 解析流程

当你在浏览器输入 `www.example.com`：

1. 浏览器查缓存（浏览器缓存 + OS hosts 文件）
2. 如果未命中 → 查询 **递归 DNS 服务器**（通常是运营商或本地 DNS）
3. 递归服务器查询 **根服务器** → 找到 TLD 服务器
4. TLD 服务器返回权威 DNS 服务器地址
5. 权威 DNS 返回最终 IP
6. 递归服务器缓存结果，并返回给浏览器
7. 浏览器向该 IP 发起 HTTP 请求

> ⚡ 小技巧：DNS 解析通常被缓存，TTL（Time To Live）决定缓存时长。

---

## ⚡ 四、DNS 性能优化与加速

1. **本地缓存**：减少重复解析
2. **DNS 服务器选择**：

   - 公共 DNS：Google `8.8.8.8`, Cloudflare `1.1.1.1`, 阿里 `223.5.5.5`
   - 企业 DNS：内部域名解析

3. **CDN + Anycast DNS**：

   - 静态资源用 CDN 加速
   - Anycast DNS 可以就近解析，提高速度和可用性

4. **DNS 预解析**：

   - HTML 中 `<link rel="dns-prefetch" href="//example.com">` 提前解析

5. **HTTPS 与 DoH（DNS over HTTPS）**：

   - DoH / DoT 提高安全性，防止 DNS 污染和篡改

---

## 🔒 五、DNS 安全问题

1. **DNS 劫持 / 污染**：

   - 将域名解析到错误 IP，常见在公共 Wi-Fi 或 ISP 层

2. **DNS 放大攻击**：

   - DDoS 攻击方式，利用开放 DNS 服务器发送大量流量

3. **DNSSEC**：

   - 数字签名验证 DNS 响应的真实性，防止篡改

---

## 🧠 六、DNS 与前端开发的关系

- **跨域问题**：CORS、子域名访问受 DNS 影响
- **CDN 部署**：DNS 决定用户访问最近节点
- **HTTPS / TLS**：域名验证依赖 DNS 正确解析
- **性能优化**：DNS 解析时间是页面首屏加载时间的一部分

---

✅ 总结一句话：

> DNS 就是互联网的“域名解析系统”，将人类可读域名转化为机器可用 IP，同时影响访问速度、安全和可用性。

# http 缓存

**HTTP 缓存**，这是前端性能优化和资源加载加速的核心手段。

---

## 🧩 一、HTTP 缓存的作用

- 减少重复请求，提高页面加载速度
- 降低服务器压力
- 减少带宽消耗
- 改善用户体验，尤其是弱网环境

> 浏览器缓存是基于 HTTP 协议和资源响应头实现的，不同策略决定了资源是否可复用或何时更新。

---

## 🏗️ 二、缓存分类

### 1️⃣ 强缓存（Cache-Control / Expires）

**原理**：浏览器直接使用缓存，不向服务器发送请求，直到缓存过期。

#### 1.1 Cache-Control（HTTP/1.1 标准）

常用指令：

| 指令           | 含义                                   |
| -------------- | -------------------------------------- |
| `max-age=秒数` | 缓存有效时间                           |
| `public`       | 所有人可缓存                           |
| `private`      | 只有浏览器可缓存                       |
| `no-cache`     | 必须向服务器验证缓存有效性（仍可缓存） |
| `no-store`     | 不缓存资源                             |

**示例**：

```http
Cache-Control: public, max-age=3600
```

- 表示资源可缓存 1 小时

#### 1.2 Expires（HTTP/1.0）

```http
Expires: Wed, 09 Oct 2025 20:00:00 GMT
```

- 过期时间点
- 已被 Cache-Control 替代，但仍被浏览器支持
- 注意：客户端时间不准可能影响缓存策略

✅ **强缓存特点**：

- 浏览器直接使用缓存
- 不发请求给服务器
- 性能最好

---

### 2️⃣ 协商缓存（Conditional Request）

**原理**：浏览器每次向服务器发送请求，服务器判断资源是否改变，如果没变返回 **304 Not Modified**，浏览器使用缓存。

#### 2.1 ETag

- 资源唯一标识（hash、版本号）
- 浏览器请求时发送：

```http
If-None-Match: "abc123"
```

- 服务器返回：

```http
ETag: "abc123"
```

- 如果匹配 → 304 Not Modified

#### 2.2 Last-Modified

- 资源最后修改时间
- 浏览器请求时发送：

```http
If-Modified-Since: Tue, 08 Oct 2025 12:00:00 GMT
```

- 服务器比对 → 返回 304 或新内容

✅ **协商缓存特点**：

- 节省流量，仍需向服务器验证
- 适合经常更新的资源

---

### 3️⃣ 浏览器缓存流程

1. 浏览器请求资源
2. 检查 **强缓存**：

   - 未过期 → 直接使用缓存
   - 已过期 → 发送请求

3. 服务器检查 **协商缓存**：

   - 资源未修改 → 返回 304
   - 资源修改 → 返回新资源

---

## ⚡ 三、缓存策略推荐

| 资源类型        | 建议缓存策略                                                                |
| --------------- | --------------------------------------------------------------------------- |
| JS/CSS/静态文件 | 长缓存（1 年） + 文件名带 hash → Cache-Control: max-age=31536000, immutable |
| 图片 / 视频     | 长缓存 + hash                                                               |
| HTML 页面       | 短缓存或 no-cache + ETag → 保证内容更新及时                                 |
| API 接口        | 一般不缓存，或使用协商缓存 / CDN 缓存                                       |

---

### 1️⃣ SPA 项目优化实践

- **静态资源**使用 hash 文件名 + 长缓存
- **HTML**使用短缓存或协商缓存
- **图片**尽量使用 CDN + 长缓存

示例：

```http
# app.abc123.js
Cache-Control: public, max-age=31536000, immutable

# index.html
Cache-Control: no-cache
ETag: "index-1.0.3"
```

> 用户刷新页面时，如果 HTML 文件没更新，浏览器通过协商缓存请求 JS/CSS 新 hash 文件

---

### 2️⃣ CDN 缓存优化

- 静态资源通过 CDN 缓存，加速全球访问
- 搭配 Cache-Control + hash 文件名，保证更新及时

---

### 3️⃣ 强缓存 + 协商缓存结合

- 推荐组合策略：

  1. **静态文件** → 强缓存 + hash
  2. **HTML / API** → 协商缓存，保证更新

- 达到 **性能最大化 + 更新及时**

---

## 🧠 四、总结

1. **强缓存**：浏览器直接使用，不请求服务器

   - Cache-Control / Expires

2. **协商缓存**：浏览器发送请求，服务器返回 304 或新资源

   - ETag / Last-Modified

3. **最佳实践**：

   - JS/CSS/图片 → 长缓存 + hash
   - HTML → 短缓存 + 协商缓存
   - API → 一般不缓存或使用协商缓存
