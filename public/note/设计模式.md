# 设计模式

在软件工程中，**设计模式（Design Patterns）**是前人总结出的**可复用、可维护的软件结构和解决方案**。它们不依赖具体语言，但常用于面向对象编程（OOP）。设计模式可以帮助你**写出清晰、可扩展、易维护的代码**。

通常设计模式分为三大类：**创建型、结构型、行为型**。下面我给你整理一份常用设计模式列表，并附简单说明和适用场景。

---

## 一、创建型模式（Creational Patterns）

**核心思想：关注对象的创建方式**，让对象创建与使用解耦。

| 模式                             | 描述                                                           | 常用场景                           |
| -------------------------------- | -------------------------------------------------------------- | ---------------------------------- |
| **单例（Singleton）**            | 保证类只有一个实例，并提供全局访问点                           | 日志系统、全局配置、线程池         |
| **工厂方法（Factory Method）**   | 定义接口创建对象，让子类决定实例化哪一个类                     | 插件系统、UI 控件创建              |
| **抽象工厂（Abstract Factory）** | 提供创建一系列相关对象的接口，而无需指定具体类                 | 跨平台 UI 框架（Windows/Mac 风格） |
| **建造者（Builder）**            | 将一个复杂对象的构建与表示分离，使同样的构建过程可创建不同表示 | 复杂对象（如 HTML 文档、SQL 查询） |
| **原型（Prototype）**            | 用原型实例指定创建对象的种类，并通过拷贝创建新对象             | 对象克隆、高性能对象生成           |

---

## 二、结构型模式（Structural Patterns）

**核心思想：关注类或对象之间的组合**，让系统更灵活。

| 模式                  | 描述                                         | 常用场景                             |
| --------------------- | -------------------------------------------- | ------------------------------------ |
| **适配器（Adapter）** | 将一个类的接口转换成客户希望的另一个接口     | 接口不兼容时（旧系统/第三方库）      |
| **桥接（Bridge）**    | 将抽象部分与实现部分分离，使两者可以独立变化 | 图形库抽象绘图 API                   |
| **组合（Composite）** | 将对象组合成树形结构表示“部分-整体”关系      | 文件系统、UI 组件树                  |
| **装饰（Decorator）** | 动态地给对象添加功能，而不改变其结构         | Java I/O 流、前端 HOC                |
| **外观（Facade）**    | 为子系统提供统一接口，简化使用               | 系统初始化、复杂库封装               |
| **享元（Flyweight）** | 共享对象以减少内存开销                       | 文本编辑器字符对象、游戏中的子弹对象 |
| **代理（Proxy）**     | 为其他对象提供代理以控制访问                 | 缓存代理、远程代理、权限控制         |

---

## 三、行为型模式（Behavioral Patterns）

**核心思想：关注对象间的职责与交互**，让行为分布合理、易扩展。

| 模式                                  | 描述                                               | 常用场景                        |
| ------------------------------------- | -------------------------------------------------- | ------------------------------- |
| **策略（Strategy）**                  | 定义一系列算法，将每个算法封装起来，使它们可互换   | 支付方式切换、排序算法切换      |
| **模板方法（Template Method）**       | 定义算法骨架，允许子类实现部分步骤                 | 业务流程抽象化、框架钩子        |
| **观察者（Observer）**                | 定义对象间一对多依赖，当对象状态改变时通知依赖对象 | 事件系统、数据绑定、React Hooks |
| **状态（State）**                     | 允许对象在内部状态改变时改变行为                   | UI 状态管理、游戏角色状态机     |
| **职责链（Chain of Responsibility）** | 让多个对象都有机会处理请求，形成链式处理           | 表单验证、日志处理              |
| **命令（Command）**                   | 将请求封装为对象，从而支持参数化和队列化请求       | 撤销/重做、任务调度             |
| **中介者（Mediator）**                | 用一个中介对象封装对象间的交互                     | 聊天室消息分发、UI 组件通信     |
| **访问者（Visitor）**                 | 封装作用于对象结构的操作，解耦操作与对象           | AST 遍历、数据分析              |
| **解释器（Interpreter）**             | 给定语言定义解释器，解析和执行句子                 | SQL、正则表达式解析             |

---

## 四、总结

- **创建型** → 关注**如何创建对象**
- **结构型** → 关注**如何组织类和对象**
- **行为型** → 关注**对象之间如何交互和分配责任**

---

💡 **小提示**：

- 不必死记硬背所有模式，重点理解**模式背后的思想**：解耦、复用、可扩展、可维护。
- 在实际开发中，经常用的模式：**单例、工厂、策略、观察者、装饰、代理**。

# 状态模式

好的，我们来详细讲讲**设计模式中的“状态模式（State Pattern）”**，这是行为型模式中非常经典的一种。

---

## 一、状态模式的核心思想

> **允许对象在内部状态改变时改变它的行为，看起来像修改了对象的类。**

简单说：

- 对象的行为会随着内部状态的不同而不同；
- 通过把状态封装成独立的对象来管理不同状态的行为；
- 避免大量的 `if/else` 或 `switch` 判断。

---

## 二、状态模式的组成

状态模式通常由三个角色组成：

| 角色                            | 作用                                       |
| ------------------------------- | ------------------------------------------ |
| **Context（环境类）**           | 持有当前状态的引用，维护状态之间的切换接口 |
| **State（抽象状态类/接口）**    | 定义状态共有的行为接口                     |
| **ConcreteState（具体状态类）** | 实现不同状态下的具体行为，决定状态切换     |

---

## 三、结构示意

```
Context
 ├─ setState(state)
 └─ request() -> state.handle(this)

State (interface)
 └─ handle(context)

ConcreteStateA
 └─ handle(context) { ...context.setState(ConcreteStateB)... }

ConcreteStateB
 └─ handle(context) { ...context.setState(ConcreteStateA)... }
```

- `Context` 持有一个 `State` 对象；
- `ConcreteState` 实现具体行为，并可以通过 `Context.setState` 切换状态；
- 客户端调用 `Context.request()` 时，行为由当前状态决定。

---

## 四、一个直观例子

假设我们有一个 **电梯系统**：

### 1️⃣ 抽象状态

```ts
interface ElevatorState {
  openDoor(): void;
  closeDoor(): void;
  run(): void;
}
```

### 2️⃣ 具体状态

```ts
class OpenState implements ElevatorState {
  openDoor() {
    console.log("门已经开着");
  }
  closeDoor() {
    console.log("关门");
    context.setState(new ClosedState());
  }
  run() {
    console.log("门开着，不能运行");
  }
}

class ClosedState implements ElevatorState {
  openDoor() {
    console.log("开门");
    context.setState(new OpenState());
  }
  closeDoor() {
    console.log("门已经关着");
  }
  run() {
    console.log("电梯运行");
  }
}
```

### 3️⃣ 环境类

```ts
class Elevator {
  private state: ElevatorState;

  constructor() {
    this.state = new ClosedState();
  }

  setState(state: ElevatorState) {
    this.state = state;
  }

  openDoor() {
    this.state.openDoor();
  }
  closeDoor() {
    this.state.closeDoor();
  }
  run() {
    this.state.run();
  }
}
```

使用时：

```ts
const elevator = new Elevator();
elevator.run(); // 电梯运行
elevator.openDoor(); // 开门
elevator.run(); // 门开着，不能运行
```

✅ 不用在每个方法里写大量 `if` 判断，状态逻辑都封装在各自的类里。

---

## 五、状态模式的特点

**优点：**

1. **封装变化**：将不同状态的行为封装成独立类。
2. **减少条件判断**：避免复杂的 `if/else` 或 `switch`。
3. **易扩展**：增加新状态无需修改现有类，只需新增 `ConcreteState`。
4. **符合开闭原则**：对扩展开放，对修改关闭。

**缺点：**

1. **类增多**：状态多时，类数量可能增加很多。
2. **状态切换逻辑分散**：需要在状态类中显式维护状态切换。

---

## 六、常见应用场景

| 场景             | 说明                                   |
| ---------------- | -------------------------------------- |
| UI 组件          | 按钮、切换开关的不同状态逻辑           |
| 游戏开发         | 角色状态机：Idle / Run / Jump / Attack |
| 网络请求         | 请求状态：Pending / Success / Error    |
| 电梯、交通信号灯 | 明确状态转换规则                       |

---

💡 **总结**：

- 状态模式是“行为随状态改变而改变”的解决方案；
- 将状态逻辑封装到独立类中，提高可维护性；
- 适用于状态复杂、行为随状态变化明显的场景。

# 观察者模式

好的，我们来详细介绍 **设计模式中的“观察者模式（Observer Pattern）”**，这是行为型模式中非常常用的一种。

---

## 一、观察者模式的核心思想

> **定义对象之间的一对多依赖，当一个对象的状态发生变化时，所有依赖它的对象都会收到通知并自动更新。**

简单说：

- 有一个 **被观察者（Subject）**；
- 有多个 **观察者（Observer）**；
- 当被观察者状态变化时，观察者会自动得到通知并作出响应。

---

## 二、观察者模式的组成

| 角色                                   | 作用                                                             |
| -------------------------------------- | ---------------------------------------------------------------- |
| **Subject（主题/被观察者）**           | 保存观察者列表，提供添加、删除观察者的接口，状态变化时通知观察者 |
| **Observer（观察者）**                 | 定义响应接口，接收被观察者的通知                                 |
| **ConcreteSubject / ConcreteObserver** | 具体实现，被观察者维护具体状态，观察者实现具体响应逻辑           |

---

## 三、结构示意

```
Subject
 ├─ attach(observer)
 ├─ detach(observer)
 └─ notify()

Observer (interface)
 └─ update(subject)

ConcreteSubject
 └─ state
 └─ notify() -> 调用所有 observer.update(this)

ConcreteObserver
 └─ update(subject) { 根据subject.state更新自己 }
```

- **被观察者**维护观察者列表；
- **观察者**实现 `update()` 接口；
- 状态变化时，调用 `notify()` 通知所有观察者。

---

## 四、一个直观例子

假设我们有一个 **新闻订阅系统**：

### 1️⃣ 抽象主题

```ts
interface Subject {
  attach(observer: Observer): void;
  detach(observer: Observer): void;
  notify(): void;
}
```

### 2️⃣ 抽象观察者

```ts
interface Observer {
  update(news: string): void;
}
```

### 3️⃣ 具体主题

```ts
class NewsAgency implements Subject {
  private observers: Observer[] = [];
  private news: string = "";

  attach(observer: Observer) {
    this.observers.push(observer);
  }
  detach(observer: Observer) {
    this.observers = this.observers.filter((o) => o !== observer);
  }

  setNews(news: string) {
    this.news = news;
    this.notify();
  }

  notify() {
    this.observers.forEach((o) => o.update(this.news));
  }
}
```

### 4️⃣ 具体观察者

```ts
class NewsSubscriber implements Observer {
  constructor(private name: string) {}
  update(news: string) {
    console.log(`${this.name} 收到新闻: ${news}`);
  }
}
```

### 5️⃣ 使用示例

```ts
const agency = new NewsAgency();
const alice = new NewsSubscriber("Alice");
const bob = new NewsSubscriber("Bob");

agency.attach(alice);
agency.attach(bob);

agency.setNews("新产品发布啦!");
// 输出：
// Alice 收到新闻: 新产品发布啦!
// Bob 收到新闻: 新产品发布啦!
```

✅ 被观察者状态变化时，观察者自动收到通知，无需主动轮询。

---

## 五、观察者模式的特点

**优点：**

1. **解耦**：主题和观察者之间只通过接口交互，彼此独立。
2. **易扩展**：增加新的观察者无需修改主题。
3. **实时响应**：状态变化时自动通知，适合事件驱动场景。

**缺点：**

1. **可能造成过度通知**：观察者太多时，性能消耗大。
2. **观察者顺序不确定**：通知顺序可能无法控制。
3. **循环依赖问题**：观察者更新可能又触发主题变化，需注意防止死循环。

---

## 六、常见应用场景

| 场景                | 说明                                                |
| ------------------- | --------------------------------------------------- |
| GUI 框架            | 按钮点击、输入框变化事件                            |
| 事件总线 / 发布订阅 | 消息通知、日志收集                                  |
| 数据绑定            | MVVM 框架中数据变化自动更新视图（如 Vue、Knockout） |
| 异步任务回调        | Promise.then / RxJS / Observer Pattern              |

---

💡 **总结**：

- 观察者模式是“一对多依赖关系”的解决方案；
- 通过接口解耦主题和观察者；
- 非常适合事件驱动或异步通知场景。
