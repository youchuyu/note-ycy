# 微前端

## 🧩 一、什么是微前端（Micro Frontends）

**微前端**是一种将大型前端应用**拆分成多个独立可运行子应用（子前端）**的架构理念。
它借鉴了**微服务（Microservices）**的思想，把前端项目从“单体巨石式应用”中解耦出来，使各部分可以**独立开发、独立部署、独立运行**。

> 🎯 简单理解：
> 微前端 = “一个前端项目由多个小项目拼起来的整体”。

---

## 🧱 二、为什么需要微前端

当一个前端项目越来越大（例如企业级后台系统、门户系统、SaaS 平台），会出现：

- 不同团队维护不同模块，代码耦合严重；
- 技术栈升级困难（React 想升级但老模块还用 jQuery）；
- 打包体积庞大，发布周期冗长；
- 不同业务模块之间需求冲突频繁。

而微前端能解决这些问题，使得：

- 各团队能**独立开发、独立发布**；
- 各模块可用不同技术栈（React / Vue / Angular 共存）；
- 主应用负责框架、路由和通信，子应用只关注业务；
- 系统整体仍能像一个完整的前端运行。

---

## ⚙️ 三、微前端的核心思想

1. **独立运行**
   每个子应用可单独启动、构建和部署。

2. **统一接入**
   主应用（Base App）负责注册和加载子应用。

3. **隔离性**
   子应用间样式、路由、状态互不干扰。

4. **通信机制**
   主应用与子应用之间可通过事件总线或共享 store 交互。

---

## 🧭 四、常见实现方案

| 实现方式                      | 描述                                       | 优点                   | 缺点             |
| ----------------------------- | ------------------------------------------ | ---------------------- | ---------------- |
| **iframe**                    | 每个子应用通过 iframe 加载                 | 隔离强、简单           | 通信复杂、体验差 |
| **Webpack Module Federation** | 各应用间动态共享模块                       | 性能好、原生支持       | 需要 webpack 5   |
| **Single-SPA**                | 一个微前端框架，支持注册多个子应用         | 成熟生态、兼容多技术栈 | 集成复杂         |
| **Qiankun**（乾坤）           | 基于 Single-SPA 的中国社区方案（蚂蚁集团） | 支持沙箱、资源加载完善 | 打包配置略重     |
| **EMP / Wujie / Garfish**     | 腾讯系等新方案                             | 性能更优、API 更现代   | 成熟度略低       |

---

## 🧩 五、典型架构示意

```
主应用（Shell App）
 ├── 导航栏 / 头部 / 公共资源
 ├── 子应用1：/user
 ├── 子应用2：/order
 └── 子应用3：/report
```

当用户访问 `/user` 时，主应用加载对应子应用的资源（HTML/JS/CSS），渲染在主容器中。

---

## 🔄 六、微前端之间的通信

常用方式：

1. **CustomEvent / window.postMessage**：原生事件通信；
2. **全局状态管理（Redux / Zustand / RxJS）**；
3. **主应用提供全局 API**；
4. **共享依赖（如 Module Federation 动态导入）**。

---

## 🧰 七、开发与部署流程

1. 各子应用独立开发（可独立运行）；
2. 主应用通过配置注册子应用入口；
3. 打包时各自构建；
4. 部署时独立上线；
5. 主应用通过动态加载资源实现集成。

---

## 🚀 八、优缺点总结

**优点：**

- 模块独立、协作高效；
- 技术栈可渐进式演化；
- 部署更灵活；
- 降低单体复杂度。

**缺点：**

- 架构和部署复杂度上升；
- 公共依赖可能重复加载；
- 样式、路由、状态隔离需要额外处理；
- 调试和本地开发更麻烦。

---

## 🧱 九、常见应用场景

- 企业级后台系统（如多个业务中心）；
- SaaS 平台、运营管理平台；
- 多团队协作的大型前端项目；
- 需要渐进式重构老系统的项目。

---

# 隔离

非常好的问题 👍 ——\*\*隔离（Isolation）\*\*是微前端架构的关键核心之一。

微前端中常说的“隔离”主要分为 **三种类型**：

1. **样式隔离**
2. **JS 运行环境隔离**
3. **路由 / 状态隔离**

下面我们逐一拆解，并总结常见的实现方案 👇

---

## 🧩 一、样式隔离（Style Isolation）

### 1️⃣ Shadow DOM 隔离

**思路：**
每个子应用挂载在一个独立的 Shadow DOM 根节点下（如 Web Components）。
Shadow DOM 内部的样式不会影响外部页面。

**特点：**

- ✅ 样式完全隔离；
- 🚫 但部分样式（如第三方库全局样式）不易继承；
- 🚫 需要浏览器支持 Shadow DOM。

**示例：**

```js
const root = document.getElementById("app");
const shadow = root.attachShadow({ mode: "open" });
shadow.innerHTML = `<style>p { color: red }</style><p>独立样式</p>`;
```

**使用场景：**
Wujie、Web Components 微前端方案。

---

### 2️⃣ CSS Scope（命名空间隔离）

**思路：**
为子应用样式添加唯一前缀（scope），例如：

```css
[data-app="user"] .btn {
  color: blue;
}
```

在子应用挂载容器上添加 `data-app="user"`，确保样式局部生效。

**特点：**

- ✅ 简单、兼容性好；
- 🚫 无法隔离全局选择器（如 `body`, `html`, `*`）。

**常见做法：**

- 构建时自动添加前缀（postcss + 插件）；
- 或运行时动态重写选择器。

---

### 3️⃣ CSS Modules / CSS-in-JS

**思路：**
利用构建工具在编译时对样式生成哈希类名，例如：

```css
.btn {
  color: blue;
}
```

变为：

```css
.btn__userApp__abc123 {
  color: blue;
}
```

**特点：**

- ✅ 命名自动隔离；
- 🚫 仍需注意全局样式。

**使用场景：**
React、Vue 项目中常见的工程化方案。

---

### 4️⃣ 动态沙箱样式重写（如 Qiankun 的 patch）

Qiankun 会在运行时拦截子应用样式插入操作（如 `insertRule`、`appendChild`），
自动给选择器加上容器作用域前缀。

**特点：**

- ✅ 子应用无需修改构建配置；
- 🚫 复杂场景（如 CSS 动画 keyframes）仍需特殊处理。

---

## ⚙️ 二、JS 运行环境隔离（Script / Sandbox）

微前端核心问题之一是：**不同子应用的全局变量、原型链不能互相污染**。

### 1️⃣ Proxy 沙箱（单实例或多实例）

**思路：**
使用 `Proxy` 拦截对子应用 `window` 的访问，让每个子应用拥有自己的“伪全局对象”。

**示例：**

```js
const fakeWindow = new Proxy(window, {
  get(target, key) {
    return key in fakeWindow ? fakeWindow[key] : target[key];
  },
  set(target, key, value) {
    fakeWindow[key] = value;
    return true;
  },
});
```

**特点：**

- ✅ 高度隔离；
- ✅ 性能较好；
- 🚫 某些原生全局对象无法完全代理（如 `document`、`location`）。

**Qiankun、Wujie** 都采用这种 Proxy 沙箱机制。

---

### 2️⃣ iframe 隔离

**思路：**
最彻底的方案：直接让子应用运行在 iframe 中。

**优点：**

- ✅ 100% 隔离 JS、CSS；
- ✅ 安全；
- 🚫 性能差、通信复杂、URL 同步困难。

**使用场景：**
需要强安全隔离的系统，如内外网项目。

---

### 3️⃣ Eval / With 沙箱

**思路：**
通过 `with` 或 `eval` 在局部作用域中执行代码，使其访问受限。

**示例：**

```js
const sandbox = { window: {} };
with (sandbox) {
  eval(`window.a = 1; console.log(window.a)`);
}
```

**特点：**

- ✅ 实现简单；
- 🚫 性能差、安全性差；
- 🚫 不推荐用于生产。

---

## 🧭 三、路由与状态隔离

### 1️⃣ 路由隔离

- 子应用使用**自己的路由系统**（React Router、Vue Router），挂载在主应用的容器内；
- 主应用统一分发路由前缀，如：

  ```
  /app1/** → 子应用1
  /app2/** → 子应用2
  ```

### 2️⃣ 状态隔离

- 各子应用独立管理状态（Redux、Zustand、Pinia 等）；
- 如果需要通信，可通过：

  - `CustomEvent`
  - 全局 EventBus（Mitt / RxJS）
  - 主应用暴露的 API（如 `window.microApp.emit()`）

---

## 📦 四、常见框架隔离方案对比

| 框架                  | 样式隔离                    | JS 隔离          | 通信方式               |
| --------------------- | --------------------------- | ---------------- | ---------------------- |
| **Qiankun**           | 动态样式作用域 + Proxy 沙箱 | Proxy + 快照沙箱 | CustomEvent / 全局变量 |
| **Single-SPA**        | 手动处理                    | 无内置沙箱       | props 传递             |
| **Wujie**             | Shadow DOM + Proxy 沙箱     | 双层 Proxy       | `window.$wujie.bus`    |
| **Module Federation** | 构建时隔离                  | 模块作用域       | 共享模块机制           |
| **iframe**            | 原生隔离                    | 原生隔离         | `postMessage`          |

---

## ✅ 总结

| 隔离类型 | 常用方案                            | 特点             |
| -------- | ----------------------------------- | ---------------- |
| 样式隔离 | Shadow DOM / CSS Scope / 动态 patch | 保证样式互不污染 |
| JS 隔离  | Proxy 沙箱 / iframe / Eval 沙箱     | 保证全局变量安全 |
| 路由隔离 | 路由前缀划分 / 主从路由管理         | 各子应用独立导航 |
| 状态隔离 | 各自 store + 事件总线通信           | 避免共享状态冲突 |

---

# Proxy 沙箱

非常好的问题 👏
“**Proxy 沙箱（Proxy-based Sandbox）**” 是现代微前端架构中一个**非常核心的概念**，尤其是在像 **Qiankun、Wujie、Garfish** 这些框架中。

下面我会系统地为你讲清楚：

- Proxy 沙箱是什么
- 单实例与多实例的区别
- 实现原理与运行机制
- 优缺点和适用场景

---

## 🧩 一、什么是 Proxy 沙箱

**Proxy 沙箱** 是一种利用 ES6 的 `Proxy` 对象实现的**运行时隔离机制**。
它的目标是：

> 让每个微前端子应用在运行时拥有自己的“window 环境”，但不污染主应用或其他子应用的全局变量。

---

### 🌍 问题背景

在微前端中，不同子应用会共用同一个浏览器 `window` 对象。
如果多个应用直接往 `window` 上挂变量，就会造成：

- 全局变量污染；
- 不同应用互相覆盖；
- 应用卸载后残留副作用。

> 举例：

```js
// 子应用A
window.appName = "A";

// 子应用B
window.appName = "B";
```

如果两个子应用共用同一个 `window`，A 就会被 B 覆盖。

---

## ⚙️ 二、Proxy 沙箱的核心思想

Proxy 沙箱的思路非常巧妙：

> ✅ 通过一个“伪造”的 window 对象代理真正的 window，
> 让子应用以为自己在操作全局变量，
> 但其实这些变量被隔离在自己沙箱的代理对象中。

---

### 基本实现思路

```js
function createSandbox() {
  const fakeWindow = {}; // 子应用自己的全局变量存放处
  const proxy = new Proxy(fakeWindow, {
    get(target, key) {
      // 优先返回子应用自己的变量
      if (key in target) return target[key];
      // 否则从真实 window 获取
      return window[key];
    },
    set(target, key, value) {
      // 所有写操作都只作用在 fakeWindow 上
      target[key] = value;
      return true;
    },
  });
  return proxy;
}
```

这样子应用中执行的：

```js
window.name = "AppA";
console.log(window.location);
```

实际上：

- `window.name` 被写入 fakeWindow；
- `window.location` 是从真实 window 读取的；
- 互不影响。

---

## 🧱 三、单实例与多实例 Proxy 沙箱

在微前端中，“单实例”与“多实例”主要指 **是否支持同一个子应用被多次激活或并行运行**。

---

### 1️⃣ 单实例沙箱（SingleInstanceSandbox）

- 同一个子应用在任意时刻只有一个沙箱。
- 当子应用激活时启用代理；
- 当子应用卸载时恢复环境；
- 通常用于不需要并行运行的场景。

> **Qiankun 的 `LegacySandbox` 和 `ProxySandbox` 就是这种。**

**实现特点：**

- 一个全局 Proxy 实例；
- 激活/失活时保存和恢复全局变量；
- 较节省内存。

```js
class SingleInstanceSandbox {
  active = false;
  addedProps = new Map();

  constructor(name) {
    const fakeWindow = Object.create(null);
    this.proxy = new Proxy(fakeWindow, {
      get: (_, key) => window[key],
      set: (_, key, value) => {
        this.addedProps.set(key, window[key]);
        window[key] = value;
        return true;
      },
    });
  }

  activate() {
    this.active = true;
  }

  deactivate() {
    this.active = false;
    // 恢复环境
    this.addedProps.forEach((val, key) => {
      window[key] = val;
    });
  }
}
```

**优点：**

- 实现简单；
- 适合单实例应用（如后台系统模块切换）。

**缺点：**

- 不支持并发运行多个相同子应用；
- 状态切换可能造成变量回滚不彻底。

---

### 2️⃣ 多实例沙箱（MultiInstanceSandbox）

- 每个子应用实例都有自己独立的 Proxy；
- 可以并行运行多个相同的子应用；
- 通常用于多标签页、多窗口并发场景。

> **Wujie、Garfish** 等框架都支持这种更灵活的沙箱。

**实现特点：**

- 每个实例都有独立的 fakeWindow；
- 不会污染其他实例；
- Proxy 代理真实 window；
- 激活和销毁仅影响自身。

```js
class MultiInstanceSandbox {
  constructor(name) {
    const fakeWindow = Object.create(null);
    this.proxy = new Proxy(fakeWindow, {
      get(target, key) {
        return key in target ? target[key] : window[key];
      },
      set(target, key, value) {
        target[key] = value;
        return true;
      },
    });
  }
}
```

**优点：**

- 并行安全；
- 状态完全隔离；
- 不需恢复 window 环境。

**缺点：**

- 内存开销更大；
- 各实例共享依赖较难（要额外通信机制）。

---

## 🧩 四、真实框架中的应用

| 框架           | 沙箱实现                                                 | 特点                        |
| -------------- | -------------------------------------------------------- | --------------------------- |
| **Qiankun**    | ProxySandbox（单实例）+ SnapshotSandbox（非 Proxy 方案） | 基于 Proxy 实现全局变量隔离 |
| **Wujie**      | MultiInstanceSandbox                                     | 支持多实例并行渲染          |
| **Garfish**    | 多层沙箱（JS + CSS + DOM）                               | 更完整隔离，兼容 SSR        |
| **Single-SPA** | 无原生沙箱，需要开发者自己实现                           | 灵活但需额外封装            |

---

## 🧮 五、优缺点总结

| 特性       | Proxy 沙箱         | iframe          |
| ---------- | ------------------ | --------------- |
| 性能       | ✅ 高（同线程）    | ❌ 低（跨进程） |
| 隔离性     | ✅ JS 全局变量隔离 | ✅ 完全隔离     |
| 样式隔离   | ❌ 需手动处理      | ✅ 天然隔离     |
| 通信复杂度 | ✅ 简单            | ❌ postMessage  |
| 并行支持   | ✅ 多实例支持良好  | ✅ 天然多实例   |

---

## 🧠 六、总结一句话

> **Proxy 沙箱的本质是创建一个“假的 window”，通过 Proxy 捕获读写操作，实现运行时全局变量的隔离。**
> 单实例侧重性能与简化；多实例侧重并发与安全。

# Webpack 的模块联邦

非常好的问题 👍 —— **Webpack 模块联邦（Module Federation）** 是现代前端架构中最重要的创新之一，尤其是它几乎定义了**微前端的构建时代**。下面我来系统讲解它的原理、使用方式、架构思想与最佳实践。

---

## 🧩 一、什么是模块联邦（Module Federation）

**Module Federation（模块联邦）** 是 **Webpack 5** 引入的一项革命性特性。
它的核心目标是：

> **让多个独立构建的应用（或模块）能够在运行时共享和加载对方的代码，而无需重新打包。**

换句话说：

- 不同项目可以互相“借用”代码；
- 每个项目都可以独立部署；
- 加载发生在 **运行时（runtime）**，而不是编译时。

---

## 🧠 二、为什么要用模块联邦

在传统模式下：

- 共享代码需要通过 npm 包；
- 每个应用独立构建，重复打包；
- 微前端中常需打包整段远程 JS；
- 难以共享状态和依赖。

模块联邦解决了这些痛点，使得：

- 📦 **代码共享更高效**
- ⚡ **构建结果可独立部署**
- 🔄 **运行时动态加载远程模块**
- 🤝 **多个应用共享相同依赖版本**

---

## 🧱 三、核心概念与角色

模块联邦基于两个核心角色：

| 角色                   | 说明                             | 类比       |
| ---------------------- | -------------------------------- | ---------- |
| **Remote（远程容器）** | 暴露（expose）部分模块给别人使用 | 服务提供者 |
| **Host（宿主）**       | 加载远程模块（remotes）          | 服务调用者 |

例如：

- `app1` 暴露一个组件；
- `app2` 动态加载并使用它；
- 两者可独立部署、升级、构建。

---

## ⚙️ 四、基本使用示例

### 1️⃣ Remote 应用（暴露模块）

**webpack.config.js**

```js
const { ModuleFederationPlugin } = require("webpack").container;

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: "app1",
      filename: "remoteEntry.js", // 暴露清单
      exposes: {
        "./Button": "./src/Button", // 暴露模块路径
      },
      shared: ["react", "react-dom"],
    }),
  ],
};
```

➡️ 生成 `http://localhost:3001/remoteEntry.js`
➡️ 暴露模块 `app1/Button`

---

### 2️⃣ Host 应用（加载远程模块）

**webpack.config.js**

```js
new ModuleFederationPlugin({
  name: "app2",
  remotes: {
    app1: "app1@http://localhost:3001/remoteEntry.js",
  },
  shared: ["react", "react-dom"],
});
```

**使用远程组件**

```js
import React from "react";
const RemoteButton = React.lazy(() => import("app1/Button"));

export default function App() {
  return (
    <React.Suspense fallback="Loading...">
      <RemoteButton />
    </React.Suspense>
  );
}
```

✅ 运行时会从 `app1` 的远程入口加载 `Button` 模块。
✅ 不需要重新打包。

## 🔄 五、模块共享机制（shared）

模块联邦最强大的部分之一是共享依赖（shared）：

```js
shared: {
  react: {
    singleton: true, // 全局唯一
    requiredVersion: '^18.0.0',
  },
  'react-dom': { singleton: true },
}
```

- **singleton**：保证只加载一个版本；
- **eager**：立即加载；
- **requiredVersion**：版本约束；
- **strictVersion**：版本不匹配时报错。

> ✅ 这样不同应用之间可以共享同一个 React 实例，避免多个 React 版本冲突。

---

## 🧩 六、运行时加载原理

运行时机制大致如下：

1. 当 Host 应用访问 `app1/Button` 时，
2. Webpack 会先加载远程的 `remoteEntry.js`；
3. 该入口文件注册暴露的模块；
4. 然后按需加载相应 chunk；
5. 将模块注入到宿主的模块系统中。

**伪代码概念示意：**

```js
// 加载远程入口
await __webpack_init_sharing__("default");
const container = await window.app1;
await container.init(__webpack_share_scopes__.default);

// 获取远程模块
const factory = await container.get("./Button");
const Module = factory();
```

## 🧠 七、Module Federation vs 传统微前端

| 对比点     | 模块联邦         | 运行时微前端（qiankun 等） |
| ---------- | ---------------- | -------------------------- |
| 集成方式   | 构建时共享模块   | 运行时 iframe/沙箱加载     |
| 技术栈兼容 | 需统一打包体系   | 可混合框架                 |
| 性能       | 更快（按需加载） | 首屏略慢（整包加载）       |
| 隔离性     | 弱（共用依赖）   | 强（独立运行环境）         |
| 通信方式   | 共享代码/状态    | 消息机制                   |
| 部署方式   | 各自独立         | 各自独立                   |

> 💡 模块联邦更像“**代码层面的微前端**”，而 qiankun 是“**运行时层面的微前端**”。

## 🧮 八、进阶用法

### 1️⃣ 动态加载远程容器

可在运行时动态注册 remote：

```js
const loadRemote = async (url, scope, module) => {
  await new Promise((resolve, reject) => {
    const script = document.createElement("script");
    script.src = url;
    script.onload = resolve;
    script.onerror = reject;
    document.head.appendChild(script);
  });

  await __webpack_init_sharing__("default");
  const container = window[scope];
  await container.init(__webpack_share_scopes__.default);

  const factory = await container.get(module);
  return factory();
};
```

---

### 2️⃣ 多版本共享

可以让不同项目共享不同版本的库：

```js
shared: {
  react: {
    singleton: false,
  },
}
```

### 3️⃣ 联邦组件库共享

可以构建一个“远程组件库”，让多个系统共享 UI 组件而无需重新发布 npm 包。

## 🧱 九、常见问题与限制

| 问题               | 原因                        | 解决方案                                                       |
| ------------------ | --------------------------- | -------------------------------------------------------------- |
| 本地开发跨域       | remoteEntry.js 属于不同端口 | 用 devServer `headers: { 'Access-Control-Allow-Origin': '*' }` |
| 动态远程模块未识别 | webpack 编译时未定义 remote | 使用 `promise new Promise(resolve => ...)` 形式定义 remote     |
| React 重复加载     | shared 未设置 singleton     | 设置 `{ singleton: true }`                                     |
| 远程模块路径错误   | remoteEntry 路径错误        | 检查部署地址或 publicPath                                      |

# 样式隔离方式

在前端开发中，**样式隔离**（Style Isolation）是指将某个组件或模块的 CSS 样式限制在自身作用域，避免影响全局或其他组件。常见方式有以下几类：

---

## 1. **命名空间 / BEM 类名约定**

- 通过给类名加前缀或采用 BEM 命名规范，减少样式冲突。
- **优点**：简单、兼容性好。
- **缺点**：需要手动维护，项目大时可能仍有冲突。

**示例**：

```css
/* BEM 规范 */
.button {
  ...;
}
.button--primary {
  ...;
}
```

---

## 2. **CSS Modules**

- 每个组件的 CSS 文件通过编译生成唯一的类名（hash），实现局部作用域。
- **优点**：无需手动加前缀，自动隔离。
- **缺点**：需要构建工具支持（如 webpack、Vite）。

**示例**：

```css
/* Button.module.css */
.button {
  color: red;
}
```

```js
import styles from "./Button.module.css";
<button className={styles.button}>Click</button>;
```

---

## 3. **CSS-in-JS / Styled Components / Emotion**

- 将 CSS 直接写在 JS 中，动态生成唯一类名，绑定组件。
- **优点**：支持 JS 动态样式、主题化、props 驱动样式。
- **缺点**：增加运行时开销，需学习特定语法。

**示例（Styled Components）**：

```js
import styled from "styled-components";

const Button = styled.button`
  color: red;
`;

<Button>Click</Button>;
```

---

## 4. **Shadow DOM（Web Components）**

- 浏览器原生支持，组件有独立 DOM 树和样式作用域。
- **优点**：真正的隔离，全局样式无法穿透。
- **缺点**：学习成本高，第三方库兼容性需注意。

**示例**：

```js
const shadow = element.attachShadow({ mode: "open" });
shadow.innerHTML = `<style>p { color: red; }</style><p>Hello</p>`;
```

---

## 5. **iframe**

- 将内容放入 iframe 中，天然隔离 CSS 与 JS。
- **优点**：完全隔离，适合第三方嵌入或微前端场景。
- **缺点**：通信复杂，性能开销大，体验不如组件方式。

---

## 6. **动态前缀 / PostCSS 插件**

- 通过构建工具，在 CSS 类名前加上模块前缀，实现作用域隔离。
- 常用 PostCSS 插件：`postcss-prefix-selector`。

---

### ✅ 总结

| 方法           | 隔离强度 | 优点             | 缺点               |
| -------------- | -------- | ---------------- | ------------------ |
| 命名空间 / BEM | 低       | 简单             | 手动维护           |
| CSS Modules    | 中       | 自动隔离         | 构建依赖           |
| CSS-in-JS      | 中       | 动态样式、主题化 | 运行时开销         |
| Shadow DOM     | 高       | 完全隔离         | 学习成本高、兼容性 |
| iframe         | 高       | 完全隔离         | 性能、通信复杂     |
| PostCSS 前缀   | 中       | 构建时处理       | 依赖构建工具       |
